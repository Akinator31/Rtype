The client online¶

How the client joins the lobby of a master and plays a game of it: the same game scene as offline, fed by a RemoteSession instead of a LocalSession (A game in the client, ADR 0015). To set up a server and play, see Play online.

Code layout¶

apps/client/src/
  Online/
    LobbyClient.cpp    the connection to the lobby: TLS with the key pinned, HELLO, the requests
    OnlineScenes.cpp   the Online menu and the list of the games
  Game/
    RemoteSession.cpp  a game online: the UDP session with the instance, inputs out, world in
    Interpolation.cpp  the world drawn 100 ms in the past, between the snapshots around that time
    Prediction.cpp     the ship of the player, moved at once by its inputs, then reconciled with the game

The client has one EventLoop for its network, polled by the game loop once per frame before the engine updates: everything network runs on the thread of the game, without locks.

From the menu to the game¶

sequenceDiagram
    participant P as Player
    participant C as Client
    participant M as Master
    participant I as Instance
    P->>C: Online, server and name, Connect
    C->>M: TCP, TLS (key of server.pub pinned), HELLO
    M->>C: WELCOME
    C->>M: LIST_GAMES
    M->>C: GAME_LIST: the lobby is shown
    P->>C: Create a game, or Join
    C->>M: CREATE_GAME or JOIN_GAME
    M->>C: GAME_JOINED (UDP port, session, keys)
    C->>I: CONNECT, then INPUT 60 times per second
    I->>C: ACCEPTED, then SNAPSHOT 30 times per second

The client goes through the master to get a game, then talks to its instance directly.

  1. Online asks for the server (host:port, the port 4242 by default, [::1]:4242 for IPv6) and the name of the player. An IP address is used as it is; a host name is looked up when Connect is pressed.
  2. The key of the server is read from server.pub, next to the executable (Generate the server keys). A server that does not hold the matching private key is refused during the handshake: "This is not the expected server".
  3. The lobby lists the games of the server: Create a game (for 4 players, named after the player), Join one, Refresh, Disconnect. Escape disconnects too.
  4. The game plays a RemoteSession with what GAME_JOINED gave. When it ends, by the pause menu or because the game ended, the client leaves it (LEAVE_GAME) and shows the list again.

Everything that goes wrong is shown in a toast: a server unreachable or not the expected one, a game full, a game that crashed, the connection lost. A lobby connection lost brings the player back to the main menu.

LobbyClient¶

rtype::client::LobbyClient lobby(loop, server, pinned, "Pavel",
    {.onWelcome = [&](std::uint32_t player) { lobby.listGames(showList); },
     .onLeftGame = [&](const rtype::lobby::LeftGameMessage &left) { /* game over, crash, timeout */ },
     .onClosed = [&](const std::string &reason) { /* toast it */ }});
lobby.joinGame(id, [&](const rtype::client::LobbyClient::JoinResult &result) { /* GAME_JOINED or an error */ });
  • One callback per request. The master answers in order (lobby protocol), so each reply goes to the oldest request waiting. An ERROR goes to the callback of its request: describe(code) gives the message for the player.
  • LEFT_GAME is the reply to LEAVE_GAME, or a notification when the player did not ask (game over, crash, timeout): the latter goes to onLeftGame.
  • PING is sent after 10 seconds without sending anything, so that the master, which closes a connection silent for 30 seconds, keeps it.
  • A name is checked before connecting (std::invalid_argument): HELLO is written in a handler of the loop, where nothing may throw.

RemoteSession¶

Direction What How often
Client → instance INPUT: the input of the player, stamped with a tick, with the inputs of the 7 ticks before 60 per second, whatever the frame rate
Instance → client SNAPSHOT parts and ENTITIES_DESTROYED, into a RemoteWorld 30 and as they come
Instance → client PLAYER_JOINED, PLAYER_LEFT: the names of the players When they join and leave
Instance → client GAME_OVER, DISCONNECT, or nothing for 5 seconds: the end Once
  • The tick of an input is the one at which the game should apply it (section 9.2 of the game protocol): the tick of the latest snapshot, plus the time since it came, plus the round-trip time measured by the session, plus 2 ticks of margin. It never goes back: the game ignores an input older than the last one.
  • takeSnapshots() gives, at every frame, the world of the interpolation: the GameSessionSystem draws it as it draws the offline world, and the entities move at the frame rate.
  • Pausing does nothing online: the game goes on, and the input sent under the pause menu is empty.
  • Leaving sends DISCONNECT to the game, when the session is destroyed.

Interpolation¶

The snapshots come 30 times per second, some late, some lost; the client draws 60, 144 times per second. Drawing the newest snapshot moves the entities in jumps: still for 33 ms, then 20 units at once. Interpolation draws the world 100 ms in the past instead, between the two snapshots around that time (game protocol, 9.3):

snapshots received:   tick 40 ──────────── tick 42 ──────────── tick 44 (newest)
                                   ▲
                       drawn tick 41.3 = newest − 6 ticks (100 ms): 65 % of the way from 40 to 42
What happens What is drawn
Snapshots on time Each entity between its positions in the two snapshots around the drawn tick
A snapshot lost The same, between the snapshots that arrived: 4 ticks apart instead of 2
No snapshot for a while Each entity goes on with its velocity for 250 ms at most, then waits
An entity created It appears when the drawn tick reaches its first snapshot
An entity destroyed It disappears when the drawn tick reaches its destruction, not when ENTITIES_DESTROYED arrives 100 ms earlier

The drawn tick advances with the time of the frames, 60 ticks per second, and is nudged towards its target (newest tick − 6): a little faster when it falls behind, a little slower when it gets ahead, never backwards. The jitter of the snapshots and the drift between the clocks of the client and of the server are absorbed without a jump; after a pause of more than half a second (a window dragged, a debugger), it jumps to its target.

Interpolation is pure, without a clock nor a network: the RemoteSession gives it each world received (receive()), the destructions (destroyed()) and the time of each frame (advance()), and draws view().

Prediction¶

The interpolation draws the world 100 ms in the past, on top of the round trip: fine for the others, whose keys the player does not see, but the ship of the player itself would answer late. Prediction moves it at once instead, and the game stays the one that decides:

  1. Each input sent moves the predicted ship by one tick, with game::moveShip(), the movement of the game itself: speed, diagonals, walls. The inputs are kept with their tick.
  2. Each snapshot says where the game had the ship at its tick, every input up to that tick applied. The prediction starts again from there and replays the inputs sent for the later ticks (reconciliation). When nothing was lost, it lands exactly where it was: no correction at all.
  3. A wrong guess (an input lost without its copies, something the game saw first) moves the prediction: the ship is not teleported, the gap is drawn and fades out in a few frames. A gap of more than 120 units (the ship came back elsewhere) is applied at once.
  4. Without a ship (destroyed, waiting to come back), nothing is predicted: the game decides.
inputs sent:   12  13  14  15  16   ◄── applied at once: the ship is drawn there
snapshot of 13 from the game ──► start from its position, replay 14, 15, 16 ──► the same place, if nothing was lost

game::moveShip() (libs/game/include/rtype/game/ShipMovement.hpp) is shared with the systems of the game, and a test checks that both give the same position to the bit, over a minute of random inputs against the walls. A rule that changes how a ship moves must change there, or every snapshot would correct the prediction.

Only the movement of the ship is predicted: its shots, the hits and its destruction are drawn as the game sends them, through the interpolation.

Tests¶

tests/client_online.cpp (tag [online]) runs the client against a real master in the same process: the Lobby and the Games of r-type_server, with real instances.

  • the address of a server, and a message for every error of the master;
  • two clients welcomed, a game created, listed and joined, an error given to its request, a player who leaves;
  • a server without the pinned key refused, a server unreachable, a name refused before connecting;
  • two clients playing the same game, each moving its own ship and seeing the other's, with the names of the players, the world drawn at every frame behind the newest one, and inputs stamped ahead of the world;
  • a game that crashes reported to its player, who can create another one, and a game that stops ending the session of its player.

tests/client_interpolation.cpp (tag [interpolation]) plays a server sending 30 snapshots per second to a client drawing 144 frames per second: the world drawn 100 ms behind, an entity moving a little at every frame, with snapshots on time, irregular or lost; extrapolation then waiting without snapshots; entities appearing and disappearing when the drawn tick reaches them; a server clock running faster; a pause; and the drawn tick never going back.

tests/client_prediction.cpp (tag [prediction]) plays the client against the real rules, a Simulation with the InputBuffer of the server, the inputs and the snapshots delayed: never corrected when nothing is lost, nor when an INPUT is lost (the next ones carry its inputs); the ship answering before the game; the game ending where the prediction was; the walls; without redundancy, a lost input corrected smoothly; no ship, then back elsewhere; a correction too large applied at once; and the ticks skipped when stamping.

./build/bin/rtype_tests "[online]"
./build/bin/rtype_tests "[interpolation]"
./build/bin/rtype_tests "[prediction]"

Limits and next steps¶

  • The shots are not predicted: they leave a round trip and 100 ms after Fire is pressed. Predicting them means drawing a shot before the game creates it, then matching it with the one it sends.
  • The player sees the others 100 ms in the past and its own ship in the present: a Bydo shot can seem to miss and still hit, as in every game that predicts.
  • The names of the players are known (RemoteSession::names()) but not shown in the HUD yet.
  • One server at a time, typed by hand: no list of servers, no address remembered.
