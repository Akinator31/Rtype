Network protocol¶
Status Version 1, specified, not yet implemented
Version 1
Transport TCP with TLS 1.3 for the lobby, encrypted UDP for the games (ADR 0012, ADR 0014)

1. Introduction¶

This specification defines the binary protocol between r-type_client and r-type_server, and between the master server and its game instances. Anyone MUST be able to write a compatible client or server by reading it only.

It is split into four pages:

Page Content
This page Conventions, overview, constants, error handling, security
Lobby (TCP) The connection between a client and the master: TLS, framing, lobby messages
Game (UDP) The datagrams between a client and its game: encryption, reliability, sessions, inputs and snapshots
Master and instances The local connection between the master and the game processes it starts

Version 1 defines how to reach a game, how to exchange messages with it securely and reliably, and the messages of the game itself: the players' inputs, the snapshots of the world and the events (game, section 9).

The words used here are explained in Networking concepts.

2. Conventions¶

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be interpreted as described in RFC 2119.

  • All multi-byte integers are transmitted in network byte order (big-endian).
  • Sizes are given in bytes. Offsets start at 0.
  • Fields are written one after the other, with no padding.

2.1 Types¶

Type Size Description
u8, u16, u32, u64 1, 2, 4, 8 Unsigned integers
i16, i32 2, 4 Signed integers, two's complement
bool 1 0 is false, 1 is true. Any other value is invalid.
bytes[N] N N raw bytes
str8 1 + n A u8 length n, then n bytes of UTF-8 text, without a terminating zero

A str8 is invalid if its bytes are not valid UTF-8, or if they contain a control character (0x00–0x1F or 0x7F). Each field of type str8 gives its allowed length range.

2.2 Message tables¶

Each message is described by a table of its fields. The offset is counted from the start of the message payload, after the header of the transport. Example of the layout of the bytes 00 01 05 50 61 76 65 6C:

Offset Field Type Value
0 Version u16 00 01: 1
2 Name str8 05 50 61 76 65 6C: "Pavel"

3. Overview¶

sequenceDiagram
    participant C as Client
    participant M as Master
    participant G as Game instance
    C->>M: TCP 4242, TLS 1.3 handshake (server key pinned)
    C->>M: HELLO (version, name)
    M->>C: WELCOME (player id)
    C->>M: LIST_GAMES
    M->>C: GAME_LIST
    C->>M: JOIN_GAME (game id)
    M->>G: ADD_PLAYER (session id, keys)
    M->>C: GAME_JOINED (UDP port, session id, keys)
    C->>G: UDP: CONNECT
    G->>C: UDP: ACCEPTED (player slot)
    C-->>G: UDP: game messages
    G-->>C: UDP: game messages

The client authenticates the master with TLS, joins a game through it, and receives the UDP port and the keys of the game. It then talks to the game directly, over encrypted datagrams.

  1. The client opens a TCP connection to the master and runs a TLS 1.3 handshake. It checks that the server's public key is the pinned one (lobby, section 2).
  2. Inside TLS, the client and the master exchange framed lobby messages: the client says hello, lists the games, creates or joins one (lobby).
  3. When the client joins a game, the master draws a session id and two keys, gives them to the game process (instances), then to the client with the UDP port of the game.
  4. The client sends datagrams to that port, on the same IP address as the master. Each datagram is encrypted with the keys of the session. The first message is CONNECT; the game answers ACCEPTED (game).
  5. The TCP connection stays open while the client plays: the master uses it to tell the client when it leaves the game, or when the game ends or crashes.

4. Versioning¶

The protocol version is a u16, currently 1. It is sent by the client in HELLO, by the instance in INSTANCE_HELLO, and in the header of every datagram (as a u8).

  • A server MUST refuse a HELLO with another version, with the error UNSUPPORTED_VERSION, then close the connection.
  • A receiver MUST drop a datagram whose version is not the one of its session.
  • Any change to the layout or meaning of an existing message increases the version. Adding a new message type that older receivers can ignore does not.

6. Error handling¶

A receiver MUST NOT crash, block, or allocate memory according to a size read from the network beyond the limits of this specification, whatever it receives.

What is received TCP (lobby, instances) UDP (game)
A frame or datagram larger than the maximum Close the connection Drop the datagram
A datagram that fails authentication (wrong tag, unknown session, replayed packet number) — Drop it silently
A message too short or too long for its type, or with an invalid value Answer ERROR (MALFORMED), then close Drop the whole datagram
An unknown message type Answer ERROR (UNKNOWN_MESSAGE), keep the connection Skip the message, using its size
A message that is valid but not allowed now (for instance JOIN_GAME before HELLO) Answer ERROR with the matching code, keep the connection Ignore the message

"Drop silently" means no answer is sent: answering an unauthenticated datagram could be used to flood a third party.

7. Security considerations¶

The decisions behind this section are in ADR 0014.

Threat Mitigation
Eavesdropping TLS 1.3 on TCP; ChaCha20-Poly1305 on every datagram payload
Tampering, forged messages TLS records are authenticated; each datagram carries a tag over its header and payload
Man-in-the-middle, impersonating the server The client pins the server's public key (lobby, section 2); the datagram keys only travel inside TLS
Replay of recorded datagrams Replay window on packet numbers (game, section 4)
Spoofed source addresses A datagram without a valid tag is dropped before anything else
Amplification The game never answers a datagram that failed authentication; TCP needs a handshake before any data
Flooding, resource exhaustion Limits on connections, frames, datagrams and pending messages (table below)
Malformed messages Strict validation of every field (section 6); the decoders are fuzzed
Modified client (cheating) The server is authoritative: clients send inputs, never positions or results
Stolen server private key Generate a new key pair and distribute a new client configuration

Limits a server MUST enforce, with configurable values:

Limit Default
Lobby connections at the same time 256
Lobby connections per IP address 8
TLS handshake duration 10 s, then close
Time to send HELLO after the handshake 10 s, then close
Games at the same time Size of the game port range
Datagrams per second and per source address, before decryption 200, the excess is dropped
Reliable messages waiting for an acknowledgement, per session and direction 256, then the session is closed
Inputs kept per player 60 ticks ahead, the others are ignored

What the protocol does not hide: the sizes and timing of the datagrams and frames, and the IP addresses of the players.
