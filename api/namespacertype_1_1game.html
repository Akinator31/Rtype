Detailed Description

The components of the game.

How the ship of a player moves, in one place: the game uses it in its systems, and the client to predict the ship of its player online (docs/architecture/client-online.md).

What each ProjectileCategory does.

The messages of a game session that libs/network does not handle itself: their payloads, written and read as the game protocol says (docs/protocol/game.md, sections 8 and 9).

How the entities of the game are made and destroyed: every new kind of entity gets its function here, so that the systems and the tests make them the same way.

The position, the velocity and the collider are those of the ECS and of the physics (rtype::ecs::Position, rtype::physics::Velocity, rtype::physics::Collider): the position is the centre of the entity.

The sessions of libs/network (ClientSession, SessionHost) carry them with their type; here they become bytes and back.

// Game: one SNAPSHOT per part, for one client
for (const rtype::game::SnapshotPart &part : rtype::game::splitSnapshot(simulation.snapshot(), lastInput))
{
host.send(session, rtype::game::message_type::Snapshot, rtype::game::encode(part),
rtype::network::Delivery::Unreliable);
}
// Client: in the message handler of its ClientSession
if (type == rtype::game::message_type::Snapshot) {
if (const auto part = rtype::game::decodeSnapshotPart(payload)) {
world.apply(*part);
}
}

The encoders throw std::invalid_argument for a value the protocol forbids: a bug of the sender. The decoders never throw: they give nothing for a malformed payload, which the receiver drops. They are pure, so that they can be fuzzed.

A C++ enum has no methods: the behavior of a category is a function that takes it, one switch per question, so that adding a category means adding a case in each.

Both must give the same position, to the bit, or the prediction would be corrected at every snapshot.
